| `DD-021` | 2026-04-02 | End-to-end dynamic run times remain too long for practical live-thermo iteration; shifting away from PR-backed table thermo has not produced a usable runtime breakthrough. | `Open (High)` | This issue is intentionally about efficiency rather than correctness. `DD-001` mitigated the original table-runtime problem by introducing `table-pool`, but `DD-007` now leaves the current PR-backed table path unsuitable as the primary thermo mode for the difficult column cases. Fresh live-thermo runs also still carry substantial startup cost (`~10-12 min` historically on the depropanizer branch), and the water-methanol UNIFAC benchmark on 2026-04-02 showed that even after parity/runtime cleanup the live path remains slow: the 10-stage `60 s` parity run with `dwsim + unifac` and `thermo_every=5` completed in about `1920.8 s` wall time (`~32.0 min` total, `~31.6 wall-s / sim-s` from `1 -> 60 s`). Direct live DWSIM flash microbenchmarks on the same seeded internal tray states showed no decisive non-PR package win: mean 8-tray sweep times were all in roughly the same band for `unifac` (`~10.56 s`), `nrtl` (`~10.38 s`), `uniquac` (`~10.45 s`), `raoult` (`~10.46 s`), and `srk` (`~11.12 s`), while live `pr` was actually slower in this benchmark (`~15.52 s`). A single full seeded parity-style `column_rhs` call with live UNIFAC was about `24.96 s`, which strongly suggests that live tray-flash work is the largest single wall-clock contributor, with additional property/Cp/helper flashes making up much of the remainder. Older depropanizer DWSIM evidence was worse still (`20260221_105557` needed about `487.7 s` wall for only `0.2 s` simulated marching; `20260331_234952` spent hours in startup). The current contributors to long runtime now look fairly clear: repeated live tray-flash sweeps during startup and marching, heavy per-step thermo/property refreshes even in simplified parity operation, inherently expensive activity-coefficient flash work for nonideal systems like water-alcohol, lack of a trustworthy fast surrogate after the PR-table regressions, and the fact that the live DWSIM path is currently scalar rather than batch/parallel in this repo. Commercial simulators typically make this tractable by reducing the number of full thermo solves rather than simply doing the same solves faster: they lean on warm starts from the previous state, sequential-modular or inside-out style updates, selective property refreshes instead of full tray reflashes at every substep, tear-stream/recycle acceleration, and highly tuned compiled thermo/property kernels. Our current live path does much less of that optimization, so backend cost is being exposed more directly. The newest diagnosis also suggests that one of the better near-term levers is richer thermo-packet reuse: cache and selectively reuse per-tray `K`, `HL`, `HV`, `Z`, and where available `cpL/cpV`, instead of recomputing those needs through separate calls. That strategy should be applicable to hydrocarbon cases as well, likely with even safer reuse thresholds than strongly nonideal water-alcohol systems. Current conclusion: runtime remains a first-class product issue. Startup trimming, parity cleanup, and switching DWSIM property packages have improved diagnosability and removed outright hangs, but they have not yet produced a practical live-thermo workflow. The next real breakthrough likely requires either a reworked trustworthy surrogate path, a more efficient non-DWSIM live backend, or a larger architectural reduction in live thermo call count. |
